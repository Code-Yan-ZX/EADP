# E4-C 四预算性能扩面：只读可行性审计

状态：设计建议，尚无扩面运行授权或新性能结论。既有 `e4_c_budget_ttft_pilot_v3/` 源码和证据均未改动。这里的“完整”仅指 DEV 成本诊断；用户方案要求候选锁定后另用 FINAL 每任务 64 图复测，不能把本报告或 DEV 面板当 FINAL 终验。

## 样本、工作量和测量单元

固定 Qwen3-VL-8B、BF16/FA2、单 A40 独占、batch=1、单模型；每任务从冻结 DEV 图像组按事先确定且与答案/性能无关的规则取 64 图，每图一题，共 192 图。以同图为块，将 K128/256/512/1024 及其 5 次重复按冻结 SHA256 种子顺序随机交错；自然和固定 32 token 两种长度协议各自完整运行，不把两者合并。不同预算都从原图读取与处理，执行真实视觉、作者选择器（1024 为 keep-all、零 greedy）、P3 和三路 DS，不能缓存视觉特征冒充主表。

每个预算、每任务、每协议有 64×5=320 次；每预算每协议 960 次；四预算两协议共 **7,680 次计时生成**。每任务×预算×协议各 10 题预热，即另 3×4×2×10=240 次；合计 7,920 次，不含诊断身份、失败和单独显存实验。这里是四个预算的 C-ON 新扩面，不能误认为附件中 K256 的 C-ON/C-DROP/C-SKIP 三配置的 5,760 次。自然保留 EOS、输出长度及上限；fixed32 强制严格 32 新 token，完整记录但不评分。计时先按图报告5次，再按图像组聚类重采样，保留重复与全部异常，不把960次当独立图。

## 现有证据与不可直接复用部分

- `e4_panel_v2/panel_003` 的 384×4 预算×DS 自然质量输出，连同其正式/独立证据及退出链，可作为同一 task/qid/group、图像、prompt、processor、权重、backend、生成 controls/EOS 和相同 K/DS/P3 路径的输出身份参照；不能当新运行的 TTFT。全量只存张量摘要，不能离线逐元素重建全部 DS/KV。forced32 不得假设与自然答案一致，需另建确定前缀/输出及真实位置和 KV 核验。
- E4 多预算 32图/256自然臂加8个固定decode锚，以及 3任务 K1024 native/keep-all 对照，提供诊断端点证据；适用于其已测路径和锚，不证明每个新性能调用逐元素正确。旧 K256 C-ON/C-DROP/C-SKIP 的正式 64图计时是在另一时窗、另一代码路径测得；它是独立上下文，不能直接拼接为新四K同轮配对结果。新的 K256 同轮测量仍需执行。
- 多预算 v3 三图自然 TTFT 为 12 预热+36 测量（每图每K三次），正式验收监督退出0；其正式独立复核及环境复核须以各自真实终止证明为准。只有三张短答案锚，不能当正式64图估计。v3 的 T0 在读图前、首token选出并同步后记首token；它在最终边界前 fsync 原始输出，因此记录的 completion 含日志写盘，**不是干净端到端时延**。

## 必须补齐的实现和验收

1. 在新目录制作多预算全量 schedule/worker/launcher，不能更改 v3 冻结源码。四预算、两协议、每任务10次预热及64×5的库存、随机种子、样本与预热是否重叠、配对/主要对比、warm-cache、源码/权重/输入/软件版本、输出和错误策略须在结果前冻结。明确每题是否允许复用已有诊断身份；有重复样本仅作开发观察，绝不声称独立确认。
2. 新增 fixed32 真实生成接口和在同题不同K的真实位置、rope delta、三路DS、32步cache/强制长度检查；不得拿固定32输出评分或拿自然输出长度替代。自然臂实际生成 controls/EOS、全部 token 和先前对应 E4 自然输出逐题比对；不符保留原始输出与失败，不能剔除后称全通过。先独立验证定长配置及真实32步，再进入计时。
3. 将自然和 fixed32 的完成边界移到 `generate` 真正结束并做约定同步之后、输出落盘/解码之前；此后立即持久化原始 token 和结束状态，失败不丢曝光。保留现有首token边界，分别声明图像读取/CPU预处理、prefill与 decode 的实际定义；模型加载、冷热缓存和日志开销单列。精细分项只能独立诊断/profiler，不在主计时逐层同步、复制张量或轮询 NVML。
4. 预算切换要证明一次 greedy（1024为零次）、K、保留顺序/P3、三DS、缓存和 hook 清理，不把只有哈希的全量记录叫作事后重建。为公平在同一进程交错预算时证明状态重置；显存比较改为配置独立进程，分别记录 torch allocated/reserved 峰值、NVML 进程/整卡未知项与 KV 字节，不能把同进程 allocator 历史混成各K峰值。
5. 按 v3 已验手段建立 CPU 反例、source-bound 全入口、实际同镜像无 GPU worker 前检、独立预审；正式面板有完整 journal、每小时快照、以实际进展更新时间配置足够宽的停滞门、硬截止及 TERM→stop→kill→inspect，严格检查 GPU 独占、磁盘及启动时 `now + outer_timeout + 预留验收时间 ≤ 1794065414`。正式与独立验收均要求真实监督/容器退出，再生成汇总；不可自动丢弃失败/重启掩盖已生成结果。

## 分阶段和预算

建议先 **32 图总计**（三任务约11/11/10）覆盖四K、两协议、5次重复的真实试运行：1,280 次测量，加按完整规则 240 次预热，约 1,520 次。它主要查 fixed32、长短输出、状态重置、完整日志和端点身份，并实测真实每臂/任务耗时及尾部；样本须独立于选点效果确定。32 图先明确是否来自最终冻结的 192 图；只有代码/机器状态/顺序、协议、证据、预热和接续计划在运行前完全同一且身份闭合，才可事先指定复用，否则单列 pilot 并对全192图重新测。遇到异常/不一致保留分母，不选择性补测直到结论好看。

现有 K256 三模式 5,940 作业约 6,800.63 秒（约 1.15 秒/作业，含启动）；v3 三图 48 作业监督总耗时约 95.30 秒（约 1.99 秒/作业，含准备），两者输出协议和任务构成不同，均不是四K×fixed32的可靠测时。仅按这两个粗率换算，7,920 次约 2.5–4.4 GPU小时、1,520 次约 0.5–0.8 GPU小时；这不是承诺或充分上界。建议初始排期预留完整 4–8 小时及至少1小时验收、pilot另留 1–2 小时；最终硬时限和阶段预算以通过身份门的 pilot 实测及长尾、异常恢复成本重算，不足则不启动整面板而保留计划和未完成状态。截至 2026-11-05 14:07 CST 距用户截止 2026-11-07 23:30:14 CST 约 57小时23分，不能把全部余额视为GPU空闲时间。

## 宿主环境与限制

采样确认 GPU 上无其他计算进程仅说明该瞬间；需要覆盖运行全程的设备/进程身份和复查，不能宣布 CPU/存储独占。最近三图 v3 背景快照中出现外部 Java 进程（`ps` 的 CPU 为进程生命周期均值），其瞬时CPU/IO影响未知；不擅自终止非本实验进程。外部负载、自然波动、热/冷缓存和同机并行都影响测量；计划记录运行前后和稀疏外部采样窗口、PID/CPU/IO/时钟/设备状态，标注与哪些测量有直接交叠，保留所有样本，未知就写未知。`ps`/健康快照自身会耗时，记录 query 与写盘窗口和残余未测范围，避免采样线程紧邻首token或轮询NVML污染主计时；监控不能替代真实无干扰证据。已有 K256 大面板确有健康检查及外部 Java 干扰，因此不同运行之间不做未经同轮配对的性能结论。
