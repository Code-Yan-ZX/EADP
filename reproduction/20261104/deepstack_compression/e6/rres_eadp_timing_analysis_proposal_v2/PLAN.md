# R-res vs EADP: proposed paired 32-image timing analysis

This analysis is proposed after seeing both methods' DEV quality and earlier timing. It is exploratory on the same DEV; it is not confirmation, an independent quality test, or an equal-compute claim. It does not read any label or partial timing data. This plan, implementation, source/input identities, NumPy version and synthetic tests must be frozen and independently reviewed before the performance run. No score or GT is required.

## Full denominator and timing boundaries

Use the exact frozen `e6/rres_eadp_timing_pilot_v4/schedule001.json` and its accepted 32 measured images (DocVQA 11, TextVQA 11, AI2D 10) and 30 group-disjoint warmup images, 10 per task. The actual schedule is 12 serial isolated processes: each gets five warmups followed by its fixed request sequence; over all processes exactly 60 warmups and 320 measured requests, five replicates per image per arm. Verify actual process/request identities, precise scheduled order, group, task, qid, method, phase and replicate, and actual timestamps against completed formal and independent reviewer evidence before analysis. Never treat repeated requests as independent images. Preserve and report all warmups and all individual measured observations; do not remove slow cases, outliers, nondeterministic outputs, failed checks or observed interference. Missing/duplicate/wrong arm, failed case/identity/exit, invalid timestamps, unavailable required formal or independent proof make the complete-panel analysis fail closed. Do not substitute missing samples or calculate a selected successful subset.

The request worker specifies `times={t0_ns,first_ns,generate_end_ns,response_end_ns}` in `time.perf_counter_ns`, synchronized at endpoints. Derive, per request, milliseconds from integer endpoint differences:

* TTFT = first − t0, from before image reading/processor to first token selected.
* Natural generation completion = generate_end − t0, before response text decoding.
* Decoded response completion = response_end − t0, including author text decode.

Model loading, request adapter setup and removal, queue/network/display, token persistence and validation after response are outside these endpoints. Synchronization, generation-control inspection and first-token stopping callback are inside; persistence/hashing after one response can disturb the next. Record output length, EOS/truncation and same-arm output/processor/image identity checks from the accepted records. R-res generate returns the prompt plus output and EADP uses inputs_embeds with continuation-only output; validate each against its own arm's accepted reference, never demand cross-arm identical output or slice EADP by prompt length.

## Primary descriptive comparisons

For each image, each arm and each of the three metrics take the median of that image's five repeats independently. Then on each image compute paired difference `R-res median − EADP median` in ms and paired ratio `R-res median / EADP median`; reject a zero or non-finite denominator. Within each task report its 11/11/10 paired image observations, the median of paired differences, median of paired ratios, and the separate medians and range of both arms' image medians. Show both per-image arm medians and paired differences/ratios; do not divide aggregate task medians and call it the median of paired ratios. Do not mix the three tasks into a pooled headline.

For each task, 10,000 image-group bootstrap draws with replacement of its complete set of groups; `numpy.random.default_rng(20261106)`, task order DocVQA, TextVQA, AI2D. Reuse each task's same draws for all metrics and both statistics. For every draw calculate the median of paired differences and of paired ratios; report NumPy linear 2.5th/97.5th percentiles with the exact NumPy version. This is cluster resampling, not resampling five requests, and is an uncorrected exploratory interval on a very small, already observed DEV panel. No significance, non-inferiority, causal, cross-model or general-deployment conclusion; no adaptive changes based on timing or quality.

## Observer and interruption disclosure

Bind the actual frozen observer and both execution/observer supervision histories, the process `time_namespace`, clock implementation, observer sample, query-start/query-end and first-fsync-completed intervals, supervisor health windows and manual health-check windows. Use request `[T0,response_end]` and observation `[start,end)` overlap, so observation start equal to response end overlaps but observation end equal to T0 does not. Observer first-fsync windows run conservatively from query end through first fsync end. Use exact overlap tests per individual request only when the source records the same time namespace and a verified comparable monotonic/perf clock; otherwise label overlap `unknown` and retain the request. A negative recorded-overlap result additionally requires that source coverage bounds enclose the whole request; where automatic-health monitoring coverage cannot be proven, report `unknown`. A recorded overlapping window may still be reported as such even if complete coverage is unknown. Distinguish no recorded overlap from no interference. Label observer second fsync, manual-check log fsync, unobserved subprocesses and residual host activity `unknown`; do not derive a precise monotonic window from UTC. Report all 380 requests with their absolute time boundaries, windows, marks, phase, actual endpoint values, process/arm/rep/task/qid/group and output/check status. Warmups are reported but excluded from the primary 320 measured observations.
