# Local StackTok Qwen3 K256: proposed 384-question DEV run

This is a local Qwen3 adaptation of the upstream Qwen2.5 integration at commit `571bdc6c4c6b3c92a94fe2a92e3aaf42b989cc96`, not an upstream Qwen3 method. The plan is made after the 3-anchor smoke generated outputs and passed formal (not yet independent) acceptance. Full admission requires both the final independent smoke proof and its actual supervisor exit. Missing or failed identity blocks execution.

Use all 384 frozen E1 DEV questions, once each, exactly one K256 natural generation each, with identical processor, image, prompt, model/backend and frozen E1 generation scalars/EOS. No labels or scoring during the run; preflight necessarily parses accepted E1 and E4 DEV mixed prediction journals solely for binding input and visual identity. Preserve per-question started and generated events immediately and fsync before later validation, with final record or explicit error. A failure interrupts the complete panel and leaves all evidence; never silently skip a question or score a partial panel.

Invoke the unchanged upstream selector once per question using actual user text, pre-merger 2×2 grouped features, post-merger features and author defaults; same P3 positions and three aligned DS injections as the accepted local smoke. Bind each input, 1024 spatial-grid layout, question token IDs, ordered/greedy and spatial 256 IDs, full/pruned shapes and hashes, actual prefill, mask, 3D position, delta and all 36 KV lengths on every forward, 6 generation scalars, EOS, exact output IDs and termination. Capture and verify actual injected tensors on the live forward path. Predeclare these requirements before seeing any full-panel outputs. Store only tensor hashes/summaries and actual token/index lists, not complete high-dimensional arrays; reconstructability is limited to the diagnostic anchor artifacts. Do not claim actual KV bytes can be rebuilt from lengths.

Performance changes relative to the smoke are limited to removing its redundant second identical upstream selector call, not hashing or persisting full KV contents per question, and summary-only tensor archives. CPU tests and independent source review must prove changes are confined to observations/control flow. This is a quality panel, not a timing benchmark; no speed claims follow.

Bound before launch: exclusive GPU; planned inner 7200 s, outer 7320 s, journal stale 1200 s, hourly snapshots, 90 s termination grace, explicit stop→kill→inspect, 24 GiB free disk, process allocator fraction 0.9. Launcher must reject when outer timeout exceeds `initial_plan.json` absolute user deadline and when GPU not idle; retain all failure evidence and never silently rerun. The 3-anchor run took about 170 s including setup, but is not a representative forecast. Validate processor/vision/3 DS against the same-question accepted E1 references, and bind full-panel candidate identity to its specific input before each generation.

GPU lock remains until implementation, source-bound CPU tests, independent review, actual same-image full no-GPU preflight and its own independent final review. A successful full run then needs real clean container/supervisor exit, formal no-GT acceptance and independent review; only after all questions and both reviews may a separate, independently reviewed DEV-only scoring process open labels.
