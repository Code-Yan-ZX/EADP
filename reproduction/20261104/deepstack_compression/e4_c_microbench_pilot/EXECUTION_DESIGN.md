# Single-image component pilot: implementation and admission design

This is a proposed GPU pilot, not an executable GPU approval. The old `e4_c_microbench/worker.py` deliberately has no GPU CLI. No real model or device has been used by this directory.

The sole image is the first image of the already frozen `e4_c_microbench/schedule001.json`: DocVQA DEV question 16539, group `389856c961891188878b76ead370e491d6676fdb6920ed745a2768ffeb001f36`. Exactly the first 60 schedule jobs are retained, 20 per original component; each has 3 warmups. There is no selection by observed latency. The existing `budget_plan.json` fixes inner Docker timeout 3600 s, external supervisor timeout 3720 s, progress stale bound 1200 s, graceful cleanup 90 s and hourly health snapshots. The host must independently check exclusive A40, sufficient disk, the source bundle and that current time plus 3720 s fits the original three-day deadline. Full 32-image profiling is not authorized or timed by this pilot.

Before any model construction, a CPU-only verifier should reconstruct the schedule and E1 input identity, bind the independent E1 P3-D1 and C-ON lightweight identity proofs, their exact reviewer/source hashes and clean supervisor exits, all model shard hashes, the author wrapper/pruner/config, this directory's code and CPU proof, and the parent model's processor/tokenizer configuration. The no-GPU container preflight must use the exact runtime image, working directory, mounts, environment, entrypoint and worker import chain, but without GPU device access or model construction. It must exercise the same admission as the real worker and record the actual Docker inspect configuration, no initialized CUDA, stop/kill outcomes and clean exit; its own independent final review and real supervisor exit are prerequisites for a separate GPU bundle.

The model worker must use the same reviewed Qwen3-VL 8B BF16/flash-attention-2 author backend and fixed input recipe as the accepted E1 record. The captured diagnostic call produces one artificial maximum-new-token output; that exposure must be fsynced to an append-only journal as soon as generated and must never be scored. The proposed `capture_guard.capture_one` observes the real full visual stream, all three DeepStack streams, selector order and actual injected prefill before any in-place decoder mutation. `identity_contract.validate` compares processor, full main/DS metadata, ordered/spatial IDs, input embeddings, mask, positions, rope delta and all three injected streams against the same accepted P3-D1 question. Failure stops the pilot; it cannot be relaxed to get an apparent identity pass.

`capture_guard` snapshots module hook registries and the processor, pruner and generation monkeypatch state and checks restoration even on an exception. Replay is allowed only after cleanup. `contracts.run_jobs` requires real `torch.is_inference_mode_enabled()`, checks the full structure and all tensor elements of every one of the 9 warmup and 60 measurement outputs against the captured reference, and fails immediately on mismatch. CUDA event timing and its host wall interval stop before output comparison and durable journal writing. Output equality must be truthfully described as checked at runtime; independent byte-for-byte reconstruction of each result requires separately archived reference/output arrays or per-output independently verifiable evidence, which this CPU preparation does not yet provide.

The schedule label `ds_injection` denotes construction of the visual-position mask and three-stream index-select staging only. It does not include the decoder's DeepStack add operation, and none of these separately synchronized event times is end-to-end TTFT. Record this exact scope in every result and report the profiling overhead and warm-cache condition.

The host launcher must use the existing supervised Docker lifecycle with a unique retained container, stop then kill if necessary, and independent inspect after exit; a dead Docker client is not proof of a stopped container. On signals, errors, hard timeout, missing or ambiguous inspect, a worker failure or incomplete job journal, the run fails and all evidence is retained. A CPU-only final verifier must require actual clean host supervisor and Docker exit, exclusive-device and source identities, captured task/image/processor identity, one complete diagnostic exposure, explicit cleanup success, exactly 9 successful warmups and 60 individually output-validated ordered measurements (20 each), finite event/host timings and no extra or missing jobs. The verifier itself needs source/CPU review, its own bounded supervisor, and a separate independent reviewer before any pilot measurement can be used.

Still to implement and review: a real model worker calling these primitives, E1 P3-D1 identity-only reference extraction bound to the accepted source proof, a durable full-output evidence format, two-stage host/container admission, bounded launcher and CPU verifier, plus synthetic adverse lifecycle tests and real no-GPU container preflight. Therefore there is no safe concrete GPU invocation yet.

## Implementation status after CPU010

The standalone worker (`pilot_worker.py`), host/container admission (`pilot_admission.py`), bounded launcher (`pilot_launch.py`) and CPU-only final verifier (`pilot_verify.py`) are implemented. CPU010 passed 16 synthetic tests with 58 source hashes and a real supervisor exit 0. This is not a real-model result or permission to use a GPU. The prior paragraphs describing a proposed design document the preparation stage; where they say the worker is still unimplemented, this status update supersedes them.

The worker preflight and GPU path run the same code through model-construction boundary and require separate external independent-review proofs. The currently absent preflight review must bind CPU010 and its completed supervisor; the final review must additionally bind the actual complete no-GPU container run, its supervisor and logs/exit. Host inspection checks the retained Docker container's image, process, mounts, device configuration and clean termination. A failed admission or unavailable inspection is a failure, not permission to continue.

A GPU pilot remains gated by its separate final review, the actual completed preflight, exclusive device availability, and the deadline. Parent scheduling is mandatory. Any GPU output must pass formal and independent acceptance before use. The preflight parses the accepted E1 DEV mixed journal, which contains predictions; it uses only identity fields and hashes model files. It does not use prediction fields, load the model, initialize CUDA or read GT. The diagnostic GPU call journals one generated token and never scores it.

The initial preflight001 failed before Docker creation because the CPU supervisor output argument was checked against its result file rather than its output directory; the failed supervisor is retained. CPU010 fixes and tests that command check and uses fresh preflight002.
