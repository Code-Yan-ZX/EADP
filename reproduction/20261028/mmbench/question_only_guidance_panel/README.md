# MMB fixed-group guidance diagnostic — CPU preparation only

This candidate compares the native EADP K=128 source guidance with the inactive source comment's question-only guidance on the same 16 preselected circular groups (60 pre-expanded rows). The same actual LLaVA model instance, images, complete LLM conversation, greedy generation, source math and existing three-stream-wait control are used. Only the late `texts` assignment changes in memory. The original source file is never rewritten.

All 60 source calls must finish and agree with previous accepted response **text**, previous runtime guidance hash and input geometry, and independently reconstructed CPU token/pixel references before the second arm starts. Every new call retains native output IDs before decoding, raw decoded response before observation checks, actual text-tower segment tensors, pixels, projected visual features, similarity and selection data, final mask, prepared embeddings and actual output IDs. Final CPU verification examines both arms and writes differences; it does not score, read GT, or require circular options to produce identical answer letters.

Historical MMB execution saved answers, guidance hash and geometry, but did **not** save its actual internal selection/masks, feature arrays or output IDs. Reconstructed reference input hashes are CPU evidence, not old GPU byte captures. Preparation read and hashed original TSV bytes containing GT but did not parse or use the answer column; execution uses only the sanitized eight-column TSV and frozen references. The 16 groups use an unchanged selection made independently of answers.

Question-only removes hints and options as well as changing text length and segmentation. This is an implementation-input diagnostic, not an isolated length intervention, an author-confirmed bug, or an identified paper recipe. Outputs are not benchmark accuracy. Observation adds overhead, so timings are not an efficiency benchmark.

The existing native GPU generation times for these 60 rows total about 16 seconds; two arms suggest about 32 seconds of native generation only. Model load, observers and serialization add unknown time. The 120 projected FP16 arrays alone are roughly 540 MiB uncompressed; all other captures and peak GPU memory are uncertain. Never launch while current GPU work occupies its allocation.

`prepare_plan.py` freezes source, inputs, observer, controller, verifier, tests and existing model-file identity evidence. `cpu_preflight.py` runs frozen tests using the author Torch/Python inside a network-isolated Docker container with no NVIDIA device nodes; it never starts a model or GPU. The prepared controller is a single attempt requiring a separate root-issued plan-bound allocation note; it does not create a queue or retry. It runs the source arm, then variant only after the source gate, waits for the actual worker to exit and its GPU PID to disappear, and starts the independent CPU verifier in a no-device container. Root must separately establish controller and container exit and review the resulting verification. Failures retain available raw outputs and observations. Do not treat a prepared plan or passing CPU checks as successful model execution.
