# Fixed16-image formula-to-facility diagnostic — prepared only

This plan asks whether two concrete paper/source formula differences change the actual K32 facility-location selection. It does not generate answers, read ground-truth labels, compute benchmark scores, or identify the unpublished main-table recipe. No GPU has been started for this preparation; future execution needs a separate root allocation after peer review. There is no supervisor, queue, automatic retry, or parameter search.

The original16 endpoint-spaced images and first canonical question per image are frozen from `cpu_dense_token_audit.json` and the existing real-feature CPU manifest. The three reference recipes are already completed executions: alpha1/beta1, alpha.5/beta1, and historical alpha.5/beta2. All use K32 and q=.2. This does not make any of them a certified paper recipe.

The existing2.60MB cache contains only FP32 CPU cross-modal global/dense similarities. It contains no native FP16 projected visual features, visual facility matrix, or final selected visual IDs. The recorded torch2.1.2 CPU Half linear failure prevents a faithful native projector reconstruction. This preparation does not replace it with FP32 projection plus rounding. The previous top32-importance overlap therefore remains insufficient to close the actual facility question.

The future worker loads the same v15 model with the native builder and exactly the previously declared three stream waits. Each image is preprocessed by native `process_images` and passes through native `encode_images` once at alpha1/beta1. Read-only wrappers save native cross-modal outputs and the native greedy inputs/outputs without changing their tensors or dtypes. The complete FP16 projector output and native FP32 visual similarity matrix are retained. The original encode result is the mandatory first source anchor: extracted source importance, ordered32 selected IDs, quota and final mask must all match exactly. Failure is terminal; no fallback arithmetic is allowed.

Every remaining comparison reuses that image's exact GPU global/dense similarities and facility matrix. Source importance is extracted directly as AST statements from fresh author `encode_images`; source helper methods and `greed_select` are compiled unchanged. The Eq10 control removes only the numerator1e-6, leaving every denominator, smoothing, beta, q, precision and negative-cosine operation unchanged. A restoration proof and comparison of all denominator ASTs are required.

The Eq6 control uses `torch.quantile(q=.2, interpolation='linear')`, retaining all entropies at or below the threshold including ties. It preserves the original source top15 order and appends only new threshold members in ascending original token position. This isolates the member-set change and does not certify the paper's unspecified reduction order. It intentionally differs from the previous CPU diagnostic's position-sorted entire quantile set; neither previous files nor their results are overwritten. All77 candidates, including padding/EOS, remain eligible. There is no valid-token masking experiment.

Four cases per reference recipe are fixed in advance: source, source-member/order identity, Eq6 membership only, and Eq10 numerator only. The identity filter returns the exact original source tensors unchanged. It must yield identical importance, ordered IDs and every greedy gain vector. With alpha1, Eq6 must also give exactly identical importance and selected IDs because the dense coefficient is zero. Source runs repeat after each comparison block to detect unstable replay; failure is terminal.

The worker stores importance arrays, ordered selected visual IDs, spatial-order retained IDs, quotas, the32 full greedy gain vectors, final masks, projected features, native visual matrix, cross-modal arrays and actual input FP16 pixels. A traced greedy observer only appends a detached clone of each native gain vector; removing that one AST observer restores the original. Every traced result must exactly match a separate unmodified native greedy call. The observer can change execution timing; no diagnostic timing is interpreted as efficiency. Per-image reports include final-set overlap, first ordered divergence, same-prefix check, both candidates' gains under both objectives at that step, top-two margins, exact ties, and both selected sets evaluated under each fixed weight map. Native global/dense/projected/similarity/importance tensors, every changed importance map and all gain vectors must be finite; nonfinite values are terminal failures. Source, implementation, reference, model-stat and16 image-SHA guards are checked again before a successful summary. These are selection diagnostics, not accuracy or an improvement criterion.

The candidate causal chain is explicit: formula change → importance change → near-tied marginal-gain ordering change → first greedy choice divergence → subsequent coverage path/final set change. A changed importance map with unchanged facility selection is also a valid negative result. If the16-image panel shows no set changes, that does not exclude rare changes over the full benchmark; if it shows changes, that does not establish that either formula explains the paper accuracy gap. No outcome automatically schedules a full benchmark.

`diagnose_facility.py` defaults to CPU-only hash/stat/panel/AST validation and does not import torch. `cpu_acceptance.py` checks the formulas on the existing CPU cache, exact agreement with previous source/Eq10 arrays, the two negative controls, denominator preservation, tie behavior and a clearly synthetic CPU FP32 observer-equivalence fixture. It does not test actual native facility outcomes. The prepared GPU entry requires `--execute --allocation-note PATH`; a future allocation note must contain `authorization=explicit_root_gpu_allocation`, exact run-plan SHA, run ID, GPU slot and the exact allowed other GPU PID list. That list must equal the live GPU list and contain fewer than two PIDs immediately before loading. The root still owns allocation and process coordination. Execution creates its output directory once and preserves partial/failure output without retry.

All previously frozen run plans, source files, predictions, and controls are untouched. Exact guards and implementation hashes are in `run_plan.json`. The preparation state is `prepared_only_not_allocated`; this document is not a GPU authorization.
